# Split apply jobs, then fix one failure at a time

Build the two pipelines as one shared engine with a classifier in front of it. The classifier labels each job `easy`, `website` or `needs_check`. Each platform is then cut into small stages (classify, snapshot, page state, field answer, action, verify, report). Each stage must pass or fail on saved fixtures before it touches a live site. The notes do not support the idea that keyboard-only automation is more reliable: Playwright's docs point the other way, so the backbone should be role/label locators with real mouse and keyboard events, plus a read-back check after every action. Most of what the notes say about **how to structure and test** the work is inference, because the architecture research found no direct sources for job classification, the answer bank, Telegram human-in-the-loop, or testing strategy for apply bots. What is sourced is mostly platform facts: limits, bot-detection behaviour, and flow shapes. The facts that change the design are these. LinkedIn caps Easy Apply at roughly 50 a day. Wellfound's DataDome blocks headless browsers. Indeed throws CAPTCHAs even at stealth tools. Datacenter IPs such as GitHub runners are distrusted by Cloudflare-style protection. So pipeline A (on-platform apply) belongs in the owner's real, logged-in Chrome, and pipeline B (company websites) belongs on the cloud runner, with CAPTCHA and tenant-bound portals routed to `needs_you`. The ordered problem list at the end is the practical output.

## Which evidence is sourced and which is design inference

Treat the notes as three layers of reliability. The first layer is **sourced platform facts**: caps, flow shapes, bot-detection behaviour, and selector hints from open-source bots. The second is **sourced but weak** material: vendor blogs, single-author write-ups, and search summaries that the researchers did not open. The notes flag several of these themselves, for example the Reddit thread on Naukri and the Snov.io ban advice. The third layer is **design inference**, which covers everything about how to decompose, test and observe the system. The architecture notes say plainly that job classification, the answer bank and Telegram human-in-the-loop have no sources, and the career-site notes mark a block of Workday flow details as "prior knowledge, verify".

One finding does carry quantitative support for the decomposition approach. A hybrid design, with deterministic scripts for known steps, a model only for ambiguity, and a loud signal when a deterministic contract breaks, is the common recommendation. A fully agentic flow can route around a site change and hide it, while a hybrid flags that the contract broke ([alexcloudstar](https://alexcloudstar.com/md/blog/self-healing-playwright-ai-browser-automation-2026/); [Tinyfish](https://current.tinyfish.ai/issue/6/foundations/article/5568/browser-automation-vs-web-agents)). Vendor figures put deterministic Playwright at about 3 s per run against about 20 s for an agent, and say 15-25% of scripts break within 30 days of site updates ([Scrapfly](https://scrapfly.io/blog/posts/browser-use-vs-playwright); [noqta](https://noqta.tn/blog/ai-browser-agents-browser-use-stagehand-web-automation-2026)). These are vendor numbers with no independent benchmark and none specific to job applications, so use them as direction, not as targets. The existing engine (`snap.py` to `classify.py` to `actions.py`, AI only for required unknown fields) already follows this pattern, so the work is repair and coverage, not a redesign.

There is one real conflict in the notes. Stagehand's official docs say replay falls back to inference when a cached selector no longer resolves, while a Mintlify mirror says it self-heals ([Stagehand caching](https://docs.stagehand.dev/best-practices/caching)). The notes side with the official doc. Whether to adopt Stagehand-style caching at all is not needed for this project; the relevant lesson is only that a repaired action should become a logged, promoted rule.

## Easy vs website: classify cheaply, store the evidence, never guess silently

No source covers this step directly, so the whole classifier is inference. The proposed order is: first the source board's structured signal, then the apply-URL host, and only then a rendered page read. The structured signals do exist in sourced form. On Naukri the button text "Apply on company site" marks an external redirect ([lordzohar repo](https://github.com/lordzohar/Naukri-autoapply-bot)). On Indeed "Apply now" is the on-site form and "Apply on company site" redirects ([Indeed help](https://support.indeed.com/hc/en-in/articles/115002786323)). Some Indeed scrapers expose it as data (`applyType` "Easy Apply" or "CS Apply", or `applyUrlStatus: "external"` with an `atsProvider`) ([trakk actor](https://apify.com/trakk/indeed-jobs-intelligence-scraper)). So the cheapest win is to store whatever apply-type field the scrapers already return at ingest time, instead of opening a tab to find out. For LinkedIn the Easy Apply button carries `.jobs-apply-button` with `data-live-test-easy-apply` according to one extension author ([DEV extension post](https://dev.to/member_5d0fa3ad/how-i-built-a-chrome-extension-that-auto-applies-to-100-linkedin-easy-apply-jobs-per-day-2bm7)). No source defines a reliable external-apply signal on LinkedIn, and the project's own note says guest pages hide the company link, so LinkedIn jobs of target companies need a login-side finder.

The design that follows is inference but cheap to test. Store `class`, `signal` and `url_host` with every decision, keep a third bucket `needs_check` so an ambiguous job never silently goes to one pipeline, cache the decision per board and job id, and make an easy attempt that lands on an off-platform host reclassify itself as `website` and enqueue. Test it as a table-driven unit test on about 50 saved job records per board. The notes suggest that number; treat it as a starting size.

Two routing facts decide where each class runs. Pipeline B can only reach company sites that a datacenter browser can load. LinkedIn Easy Apply needs the owner's login, and Naukri, Indeed, Internshala and Wellfound are blocked or login-gated from the cloud, which is what the project's own notes already conclude. The evidence supports that: Wellfound uses DataDome, and its bot README reports a CAPTCHA for headless browsers while headed Chrome with a real profile passed ([wellfound-bot](https://github.com/apoorvdarshan/wellfound-bot)); the Indeed bot README says Indeed "aggressively deploys CAPTCHAs ... even with bot-detection bypass techniques" and recommends Indeed for search only ([beatwad](https://github.com/beatwad/LinkedIn-AI-Job-Applier-Ultimate)). The inference that GitHub-runner IPs fare worse on Indeed has no measurement behind it, but the CI-runner risk for Cloudflare Turnstile is reported by third parties ([dev.to arsonxdev](https://dev.to/arsonxdev/i-tried-every-headless-browser-to-solve-cloudflare-turnstile-only-one-worked-1j20)).

## Pipeline A: on-platform apply is five different problems, not one

### Real input and the keyboard question

The notes do not confirm that keyboard-driven flows are more reliable. `page.keyboard.press` does not focus an element first, while `locator.press` does; locator clicks run actionability checks that a bare key press lacks ([Playwright input docs](https://playwright.dev/docs/input)). A Tab-order flow therefore fails silently when the DOM shifts, and locator actions fail loudly. The notes also could not confirm whether Playwright's input events count as trusted, so verify with a listener before relying on it. The defensible rule is: locate by role or label (the `data-fp` stamps), act with real events, verify by read-back, and use focus-type-ArrowDown-Enter only for custom comboboxes. If `fill` leaves a field empty while typing works, the page listens for key events and `pressSequentially` is the fix ([Hyperping](https://hyperping.com/learn/playwright/playwright-forms-and-inputs)). For the existing Chrome extension, the same lesson appears as dispatching pointer, mouse and click events and setting values through the native prototype setter then firing `input`, `change` and `blur` ([DEV write-up](https://dev.to/maazkhanxo/bypassing-shadow-doms-same-origin-iframes-how-i-solved-linkedins-massive-sdui-update-1lmk)). That is already in `content.js`, so the remaining work is per-platform step transitions and verification.

### LinkedIn

LinkedIn is the best documented and the riskiest. Reports disagree on where the modal lives: a same-origin iframe with shadow roots ([DEV write-up](https://dev.to/maazkhanxo/bypassing-shadow-doms-same-origin-iframes-how-i-solved-linkedins-massive-sdui-update-1lmk)), the `#interop-outlet` shadow root ([Hive skill](https://openskillindex.com/skills/aden-hive-hive-hive-linkedin-automation)), or a `<dialog>` per the project's notes. The first task is therefore to write one dialog finder that traverses all three and fails loudly if it finds none. The notes also say to read the validation error after pressing Next and use it as the retry signal, which matches the project's existing force-fill loop; this is inference from general React behaviour.

On limits, the commonly cited figure is **about 50 Easy Apply submissions per rolling 24 hours**, with the message "You've reached today's Easy Apply limit" and no reported penalty for hitting it ([LoopCV](https://loopcv.pro/guides/linkedin-easy-apply-limit)). One extension author claims 100-150 a day with restrictions above 200, which conflicts and is self-reported ([DEV extension post](https://dev.to/member_5d0fa3ad/how-i-built-a-chrome-extension-that-auto-applies-to-100-linkedin-easy-apply-jobs-per-day-2bm7)). Plan for 50 and treat more as unproven. LinkedIn's help page mentions curbing automation ([LinkedIn help](https://www.linkedin.com/help/linkedin/answer/a512353)), and the enforcement tiers run from a temporary pause to a restricted account, with the risk factors (bursts, round-the-clock activity) unconfirmed ([FastApply](https://blog.fastapply.co/can-you-get-banned-for-auto-applying-on-linkedin-2026)). The notes' inference is a cap near 25-40 a day, spaced out, in the owner's own Chrome on the owner's own IP. One project reports an auto-pause after 3 submissions in 30 minutes and a rise from 40% to 83% success by fixing 26 discrete failures over 7 runs, but that is a small, unverified sample ([gutierrez-public-lab summary](https://gutierrez-public-lab.pages.dev/experiments/2026-03-15-linkedin-submission-rate-ratchet)). The useful reading is that success came from fixing failures one by one, which is the method asked for here.

For verification, wait for "Application sent" ([DEV extension post](https://dev.to/member_5d0fa3ad/how-i-built-a-chrome-extension-that-auto-applies-to-100-linkedin-easy-apply-jobs-per-day-2bm7)); a missing "Applied" status afterwards may mean sync delay or a failed submit ([LoopCV](https://www.loopcv.pro/guides/linkedin-easy-apply-not-working/)). So an unconfirmed result should be recorded as `unknown` and re-checked, not retried, to avoid a double submit (inference).

### Naukri and Indeed

The evidence here is the thinnest. **No source documents Naukri's apply chatbot, its question types, or Indeed's smartapply steps**, and no source documents either site's apply API. Naukri's job API is gated by short-lived in-browser tokens and plain HTTP gets a recaptcha ([JobsPipe guide](https://jobspipe.dev/blog/naukri-api)), so UI automation in a real browser is the only practical path. The reference Naukri bot has no chatbot logic and counts a click as applied with no post-submit check ([Naukri-Edge.py](https://raw.githubusercontent.com/lordzohar/Naukri-autoapply-bot/main/Naukri-Edge.py)). Another extension reports falling back to a contenteditable chatbot flow ([JobPilot write-up](https://mahi.is-a.dev/work/jobpilot)). Naukri's daily quota is reported at about 100, with the text "Your daily quota has been expired." as the stop signal ([lordzohar](https://github.com/lordzohar/Naukri-autoapply-bot)). Naukri recruiters can attach custom questionnaires that interrupt the candidate ([Naukri recruiter FAQ](https://recruiterfaq.naukri.com/2016/09/16/job-posting-questionnaires)). Indeed pre-fills smartapply forms from the on-site profile, so a fuller profile means fewer questions reach the answer bank ([beatwad](https://github.com/beatwad/LinkedIn-AI-Job-Applier-Ultimate)).

Because there is nothing to copy, the first step for both sites is a capture session in the owner's browser: record the DOM and network of a real apply, save snapshots as fixtures, then write the loop. The notes' suggested shape for the Naukri chatbot is read the last bot message, answer from the bank, send with real typing, wait for the next message. That is inference, supported only by the JobPilot description.

### Internshala and Wellfound

Wellfound's apply is a modal with a note and "Send Application", which cannot be undone ([Wellfound help](https://help.wellfound.com/article/769-how-do-i-apply-to-a-job)). Screening questions exist in its data model, and the wellfound-bot refuses to proceed when a required one is unanswered ([wellfound-bot](https://github.com/apoorvdarshan/wellfound-bot)). Wellfound caps active applications (no number given) and lists spamming applications as a violation ([application limits](https://help.wellfound.com/article/767-application-limits); [enforcement FAQ](https://help.wellfound.com/article/1201-community-guidelines-enforcement-faq)). The one run reporting 171 of 178 applied with no blocks is the author's own claim. Combined with DataDome, this supports keeping Wellfound in the real logged-in Chrome with a few selective applications a day. Internshala asks "Why should you be hired?" on every application and may list assignment questions with an upload button ([Internshala blog](https://internshala.com/blog/how-to-make-a-successful-internship-application-on-internshala/)). The PyPI bot skips assignments that ask for URLs or personal links ([PyPI internshala-bot](https://pypi.org/project/internshala-bot/)), which is a good hand-to-owner rule. The notes found no Internshala ban reports or terms, and no documented "already applied" markup. The project's own live-tested selectors outrank anything in these notes.

## Pipeline B: company websites work best in order of how open the ATS is

Greenhouse, Lever, Ashby and SmartRecruiters publish open job-board APIs without a key, while Taleo, Oracle Cloud Recruiting, Phenom and iCIMS are session-bound JavaScript-heavy portals ([dev.to 42 employers](https://dev.to/get_anything/i-tested-42-large-employers-to-see-which-ones-you-can-actually-scrape-only-7-worked-535e)). A Nov 2026 crawl of 305 top employers (a curated, tech-skewed set) estimates Greenhouse at 37.7%, Workday at 24.6%, Oracle HCM and Lever at 7.5% each ([ResumeGeni](https://resumegeni.com/research/ats-market-share-2026)). Indian IT is murkier: Wipro reportedly moved to Workday and Infosys uses SuccessFactors for lateral hiring, from secondary vendor sources ([JobRise](https://jobrise.io/en/ats-checker/wipro/); [Unstop](https://unstop.com/blog/infosys-recruitment-process)). No verified ATS was found for TCS, Cognizant, Accenture or IBM, so the first job is to resolve each target company's real apply host from saved links.

The proposed playbook order is Greenhouse, Lever, Ashby, SmartRecruiters, then Workday, then everything session-bound. The single-page, no-account claim for the first group and the Workday step list are prior knowledge, not sourced, and must be verified on live pages. What is sourced for Workday is the `data-automation-id` attribute as the stable hook ([Nexthink docs](https://docs.nexthink.com/platform/user-guide/adopt/guide-creation-and-management-from-nexthink-applications/configuring-adoption-settings/use-case-element-selector-for-workday)). Playwright's default test-id attribute is `data-testid`, so configure `testIdAttribute: 'data-automation-id'` ([Playwright patterns guide](https://www.skills.lc/ed3dai/ed3d-plugins/ed3dai-ed3d-plugins-plugins-ed3d-playwright-skills-playwright-patterns-skill-md)). Workday screening questions such as salary, availability and work authorization are often not covered by autofill ([JobWizard](https://jobwizard.ai/blog/how-to-automate-workday-job-applications-with-a-chrome-extension)), and radio buttons can sit behind overlays that intercept clicks ([skillsmp job-apply skill](https://skillsmp.com/skills/neonwatty-job-apply-plugin-skills-job-apply-skill-md)). Host detection is cheap: the Workday pattern `([\w-]+)\.(wd\d+)\.myworkdayjobs\.com/([\w-]+)`, `icims.com`, `taleo.net` ([Apify ATS detectors](https://apify.com/forevertools/ats-company-jobs.md)), and for vanity domains a search of the page source for vendor strings ([withresumeai](https://withresumeai.com/ats-checker/how-to-find-ats)). Detection does not mean the form is automatable, and several detectors miss in-house portals.

### Stored passwords, OTP and Telegram

The per-host HMAC password plus a Telegram code relay matches common practice. Email-verification bots poll with a retry-and-timeout loop instead of fixed sleeps ([dev.to email verification](https://dev.to/francofuji/email-verification-bots-with-playwright-1dc7)), and a Telegram-bot-plus-Playwright system that sends a captcha image and waits for the reply shows the same pause and resume pattern ([Contra post](https://contra.com/community/sHVJceck-i-built-an-automation-system-that)). A reply-to-message-id match, persisted `waiting_human` state in D1 so the runner can exit, a 3-5 minute OTP window with one resend, and an immediate park for CAPTCHAs are all inference, with no source behind the thresholds. Reading the verification email directly via Gmail API or IMAP would remove the human from most OTPs, but that is also unsourced prior knowledge and adds a credential to store.

### Datacenter limits and success checks

Headless Chromium on GitHub Actions will hit CAPTCHA or Turnstile portals, so classify them as `blocked` and route to `needs_you` or the laptop. Nothing in the notes confirms a documented policy against GitHub-hosted runners; that remains a measured-in-practice question. Playwright's `fill` fires `input`, while `pressSequentially` is for key-event listeners and `frameLocator` enters iframes ([Playwright Locator docs](https://playwright.dev/docs/api/class-locator)). The notes offer no sourced best practice for verifying a submission; the proposal is confirmation text or URL change, Submit gone, a confirmation email, and a re-opened job showing a button-based "Applied" state. Keeping `apply_dry` until each ATS has N clean dry runs is inference, and sensible given that Skyvern-style per-job failure isolation (`continue_on_failure`) is the only sourced pattern ([Skyvern cookbook](https://www.skyvern.com/docs/cookbooks/job-application-filler)).

## Making breakage visible: fixtures, health checks and an error taxonomy

Since the system currently breaks at many points, observability is what turns a pile of failures into a work queue. The notes support three practices. Isolated tests with user-facing locators ([Playwright best practices](https://playwright.dev/docs/best-practices)). Hand-verified canary records re-checked on a schedule as the cheapest high-signal check ([Tap blog](https://taprun.dev/blog/health-contracts-catch-silent-failures.html)). Success measured on field fill rates, since HTTP 200 is not success and a null-rate jump (example 2% to 40%) signals lost selectors or soft-blocking ([DEV: selector fallbacks](https://dev.to/withatte/dynamic-selector-fallbacks-how-to-scrape-e-commerce-sites-that-change-frequently-2de8)). HAR replay with `page.routeFromHAR` is described by one third-party tutorial and should be checked against official docs ([Steve Kinney](https://stevekinney.com/courses/self-testing-ai-agents/recording-hars-for-network-isolation)).

The rest is design inference. Make each page classifier a pure function from snapshot JSON to a state, so it is tested offline in milliseconds. Capture snapshot, screenshot and HTML on every unclassified or stuck page so each production failure becomes a regression fixture. Use a failure taxonomy (classify_unknown, field_unmapped, field_fill_failed, validation_error_loop, auth_required, otp_timeout, captcha, closed_posting, already_applied, redirected_offsite, stuck_timeout, site_blocked) with one D1 `apply_events` table, and a per-site breaker that pauses a queue after 3 of the last 5 attempts fail on classification or fill errors. The thresholds are unsourced; one cited example uses a 10% error budget ([DEV: resilient DOM selection](https://dev.to/anderecit/future-proofing-your-scrapers-strategies-for-resilient-dom-selection-1j4f)). Logs must never contain typed values because the reader repo is public.

For unknown form fields, the sourced warning is that AI tools added false information to users' applications and that knockout screening questions mean automated Easy Apply often never reaches a human ([Business Insider NL](https://www.businessinsider.nl/a-free-ai-tool-can-help-you-apply-to-hundreds-of-jobs-per-day-users-said-there-are-risks-but-theyre-worth-it/)). Skipping LLM answers below a confidence of 0.7 is one bot's rule ([DEV Python bot](https://dev.to/arul_cornelious/i-built-a-linkedin-easy-apply-bot-in-python-heres-what-i-learned-about-browser-automation-4j3p)). The design that follows from this is a canonical-key answer bank, AI only for required unknown fields and only allowed to choose from bank values or offered options, never inventing CTC, years or work authorization, and a count of every unmapped label to promote weekly. All of that is inference.

## Conclusion

The notes change the question from "how do I make the bot smarter" to "which stage failed, and can I reproduce it offline". The platforms differ less in difficulty than in where they are allowed to run: pipeline A is bound to the owner's real browser by login, DataDome and CAPTCHA behaviour, and pipeline B is bound to the cloud runner by being account-per-portal and mostly open ATS forms. That makes the classifier the highest-leverage piece, since a wrong class sends a job to a place where it cannot succeed.

Two open questions need live measurement, not more research. One is whether the LinkedIn modal is an iframe, a shadow root or a dialog today. The other is whether GitHub runner IPs are blocked by the specific target portals. Every platform-specific selector claim in the notes is secondhand, so the first live capture session on each site will be worth more than any further reading.

## Ordered list of small problems to solve one by one

Each item has a pass/fail test on saved fixtures first and a live dry run second. Order is by dependency and by payoff.

1. Failure taxonomy and `apply_events` logging: add the codes, one row per attempt, snapshot plus screenshot on every unclassified or stuck page, no typed values. Test: a forced failure produces a row and a fixture. Everything below depends on this.
2. Fixture harness: pure `snapshot_json -> state` classifier tests plus a local mock-portal server for step tests. Test: existing classifier passes on 20 saved snapshots.
3. Job classifier `easy / website / needs_check`: use stored apply-type fields, board button text and apply host; store evidence; cache per job. Test: 50 labelled saved jobs per board.
4. Easy-to-website reclassification: an easy attempt that lands off-platform enqueues into pipeline B. Test: mock redirect.
5. Apply-host resolver for target companies, including the LinkedIn-hidden-link case: produce the real company host for each target. Test: 20 saved links resolve to a known ATS or `unknown`.
6. Answer bank hardening: canonical keys, label patterns, option aliases, type-aware formatting, unknown-label counter, AI constrained to bank values for required fields only. Test: 100 saved question labels mapped, zero invented numeric facts.
7. Success, already-applied and closed detection per platform, from a button or confirmation text only, never nav links. Test: saved pages with each state.
8. Limits and pacing: LinkedIn about 25-40 a day, 14 h stop on the limit message, Naukri quota text stop, Wellfound a few a day, random pauses, dedupe by normalised URL. Test: simulated limit message stops the queue.
9. LinkedIn Easy Apply dialog finder (iframe, shadow root, `<dialog>`) that fails loudly, then the step loop Next/Review/Submit with validation-error-driven retry. Test: fixtures of each container type, then one live dry run to Review.
10. Naukri capture session, then the apply-button outcome detector (chatbot, inline form, redirect), then the chatbot loop. Test: recorded chatbot transcript fixtures.
11. Indeed smartapply step loop using page-state reading and profile prefill, with CAPTCHA parked as `needs_you`. Test: saved step pages.
12. Internshala: "why hire you" and assignment questions through AI with the full JD, hand-off when an assignment asks for links or files. Test: saved form with and without an assignment.
13. Wellfound modal with note and screening questions, then the "Undo m:ss" sent signal; optionally the GraphQL read of screening questions from inside the logged-in page, after a live schema capture. Test: saved modal fixtures.
14. Telegram human-in-the-loop as persisted `waiting_human` state with reply-to-message-id matching, OTP window and one resend, CAPTCHA parked at once, resume by re-snapshot. Test: simulated reply, timeout and wrong-job reply.
15. Pipeline B playbooks in order: Greenhouse, Lever, Ashby, SmartRecruiters, each promoted from dry to live only after N clean dry runs (pick N, for example 5). Test: mock single-page forms, then one live dry run each.
16. Workday: per-tenant account flow, `data-automation-id` locators, custom dropdowns and segmented date inputs, tenant verification by link or code. Test: saved page per Workday step, then live dry runs on one tenant.
17. Per-site breaker and a weekly canary dry run per site that stops before Submit, with alerting on the `/applystatus` line. Test: three forced failures trip and recover the breaker.
18. Optional last: an AI "unclassified page" fallback that proposes one action, logged and promoted to a playbook rule only after it works. Test: a deliberately unrecognised fixture produces a logged proposal and no silent retries.
